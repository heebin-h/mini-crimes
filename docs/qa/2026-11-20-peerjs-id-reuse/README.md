# QA: PeerJS 공용 시그널링 — 끊긴 피어 id 재등록 가능 여부 (2026-11-20)

## 요약 (먼저 읽기)

- **알고 싶었던 것:** README 한계 항목의 "공용 시그널링 서버에서 끊긴 피어의 id를 다른 사람이 다시 등록하는 것도 이론상 가능하다"가 **실제로** 가능한가. (방장의 방 id는 `mini-crimes-v1-<방코드>`로 고정이고 방코드는 참가자 전원이 안다.)
- **한 것:** 공용 서버 `wss://0.peerjs.com`에 WebSocket으로 직접 접속해, 매 회 새 랜덤 id로 ① 피해자 등록 → ② 피해자가 접속 중일 때 다른 토큰으로 같은 id 등록(대조군) → ③ 피해자 연결 종료 후 다른 토큰으로 같은 id 등록, 을 **25회** 반복했다(요구: 최소 20회). 이후 요청에 따라 **추가 25회**를 같은 스크립트로 더 실행해 증명 가능한 시도는 총 **50회**다.
- **결과:** 50/50회 모두 같은 패턴 — 접속 중에는 `ID-TAKEN`으로 거부(50/50), 연결이 끊긴 뒤에는 `OPEN`으로 **탈취 성공**(50/50, 528~694ms). 예외·타임아웃 0건. (1차 25회 + 2차 25회)
- **결론:** 시그널링 서버 수준에서는 "이론상"이 아니라 **실측으로 확인된 사실**이다. 다만 게스트가 실제로 탈취자에게 붙는지, 탈취자가 가짜 방장 노릇을 하는지는 **테스트하지 않았다**(아래 한계).

## 방법

1. 시도마다 `mctheory<랜덤16자>` id를 새로 만든다. 실제 앱 접두어(`mini-crimes-v1-`)와 다르므로 실제 방과 충돌하지 않는다.
2. **① 피해자:** `wss://0.peerjs.com/peerjs?key=peerjs&id=<id>&token=<토큰A>`로 접속, 서버 메시지 `OPEN` 기대.
3. **② 대조군:** 피해자 연결을 유지한 채 **다른 토큰 B**로 같은 id 등록 시도. `ID-TAKEN`이 와야 서버가 정상적으로 id를 보호하는 것이다. 이게 `OPEN`이면 이 테스트 자체를 신뢰할 수 없다.
4. **③ 탈취 시도:** 피해자 WebSocket을 닫은 직후 **토큰 C**로 같은 id 등록. `OPEN`이면 탈취 성공, `ID-TAKEN`이면 서버가 끊긴 뒤에도 보호한 것.
5. 매 시도 사이 300ms 대기(공용 서버 부하 최소화). 등록한 소켓은 시도마다 전부 닫는다.

판정이 의미를 가지려면 ②가 거부되고 ③이 성공해야 한다(서버가 "접속 중 id"는 지키지만 "끊긴 id"는 비운다는 증거). 25회 모두 그랬다.

## 실행 이력 (정직하게)

- **1차 (같은 날, 20회):** 같은 로직으로 20회 실행해 20/20 동일 결과(`ID-TAKEN` 20, 탈취 `OPEN` 20, 671~1215ms). 그때는 시각 기록과 로그 저장이 없어 **증거 파일이 남아 있지 않다.** 대화 출력으로만 존재한다.
- **2차 (이 폴더 `run.log`, 25회):** 증명용으로 시각 기록(`startedAt`·`endedAt`)을 스크립트에 추가하고 로그를 파일로 저장해 다시 실행했다. 이 폴더의 1차 근거는 이 실행이다.
- **3차 (이 폴더의 `run-2.log`, 25회):** 사용자 요청으로 같은 스크립트를 한 번 더 실행했다. 따라서 이 폴더에서 증명 가능한 시도는 `run.log` 25회 + `run-2.log` 25회 = **50회**이고, 대화에만 남은 최초 20회는 합계에 넣지 않았다.
- 모든 실행의 결과가 같았다(예외·타임아웃 0건).

## 한계 (이 테스트가 보여주지 않는 것)

- **앱 수준 영향은 미검증.** 시그널링 서버에서 id 등록이 되는지만 봤다. 게스트 브라우저가 실제로 탈취자에게 WebRTC 연결을 맺는지, 탈취자가 게스트의 `room:join`(참가 토큰 포함)을 받아 사칭할 수 있는지는 확인하지 않았다.
- **서버 정책 변동 가능.** 공용 `0.peerjs.com`은 제3자 서비스라 정책이 바뀔 수 있다. 이 결과는 2026-11-20 13:18~13:19 UTC 시점의 관측이다.
- **단일 환경.** 한 대의 Mac, 한 번의 네트워크 경로, Node v26.4.0에서만 실행했다. 서버의 재등록 허용이 클라이언트 환경에 좌우될 가능성은 낮다고 추정하지만 다른 환경에서는 확인하지 않았다.
- **PeerJS 클라이언트 라이브러리를 거치지 않았다.** 프로토콜(WebSocket 메시지)을 직접 호출했다. 실제 앱의 `new Peer(id)` 경로도 같은 등록 프로토콜을 쓸 것으로 추정하지만 이 폴더에서 재현하지는 않았다.
- **방장 새로고침(약 0.8초 재호스팅 구간)에서의 경쟁 조건**은 시도하지 않았다. ③의 소요(528~694ms)는 "닫은 직후부터 공격자 `OPEN`까지"이며, 실제 경쟁 성공률과는 다르다.

