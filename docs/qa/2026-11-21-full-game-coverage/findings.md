# 발견 사항 · 정정 이력 · 미재현 실패

> 제품 코드는 이번 QA에서 **수정하지 않았다.** 아래 F1~F3은 재현 방법과 근거를 남기고 수정 여부는 사용자 판단에 맡긴다.

## 제품에서 확인된 동작

### F1. 노트를 입력하고 300ms 안에 새로고침·이동하면 유실된다 (확인됨, 낮음~중간)

- **근거:** `client/src/components/game/SharedNote.jsx` — 입력을 300ms 디바운스 후 `onChange`로 전달하고, 언마운트 cleanup(`useEffect(() => () => clearTimeout(...))`)이 타이머를 취소만 할 뿐 마지막 값을 flush하지 않는다.
- **재현:** E2E `메모 디바운스 경계(관찰)` — 솔로에서 입력 직후 새로고침하면 `immediate: ""`(유실), 600ms 기다린 뒤 새로고침하면 `"메모-600"`(보존). 로그: `logs/e2e-dev-full.log`.
- **영향:** 솔로는 `localStorage` 저장 전에, 팀은 `note:update` 전송 전에 페이지를 떠나면 마지막 300ms 입력이 사라진다. 팀에서 "입력하자마자 최종 제출"하는 경우도 같은 구간이다.
- **미확인:** 실제 사용자가 이 구간에서 얼마나 자주 이탈하는지.
- **수정 후보(미적용):** 언마운트·`pagehide`·제출 시 대기 중인 값을 즉시 flush.

### F2. 방 코드 앞에 공백이 붙으면 참가가 실패한다 (확인됨, 낮음)

- **근거:** `CaseSelectPage.jsx`의 방 코드 입력칸이 `maxLength={6}`이라 앞 공백이 있으면 뒤 글자가 잘린다. 진단 스크립트 `diag/join-code-variants.mjs` 결과:

  | 입력 | 입력칸 값 | 참가 |
  |---|---|---|
  | `dcrp69`(소문자) | `DCRP69` | 성공 |
  | `DCRP69 `(뒤 공백) | `DCRP69` | 성공 |
  | ` DCRP69`(앞 공백) | ` DCRP6` | **실패** — "방을 찾을 수 없습니다" |
  | `  DCRP69  `(앞뒤 공백) | `  DCRP` | **실패** |

- **영향:** 채팅·메신저에서 코드를 복사할 때 앞 공백이 같이 붙으면 "방이 없다"고 나와 방 문제로 오인하기 쉽다. 코드가 6자임을 모르는 사용자는 원인을 찾기 어렵다.
- **수정 후보(미적용):** 입력 시 공백 제거 후 길이 제한, 또는 `maxLength` 제거 후 `trim().slice(0, 6)`.

### F3. 같은 이름으로 새 탭에서 재참가하면 유예(20초) 동안 "같은 이름" 거부 (의도된 정책의 결과)

- **근거:** E2E `팀 로비` — 게스트 탭을 닫은 뒤 같은 이름·새 탭으로 참가하면 `takenDuringGrace: true`, 약 22초 후 재참가 성공. 참가 비밀 토큰(H-2)이 탭 `sessionStorage`에만 있어서, 새 탭은 토큰이 달라 끊긴 자리를 이어받지 못하고 이름 충돌로 거부된다.
- **영향:** 실수로 탭을 닫은 사용자는 20초 기다리거나 다른 이름으로 들어가야 한다. 진행 중(게임 시작 후)에도 새 탭으로는 복귀할 수 없고 같은 탭 새로고침만 복귀할 것으로 **코드상 추정**한다(`hostRoom.js` 재접속 조건이 이름+토큰이고, 토큰 없는 신규는 `GAME_ALREADY_STARTED` — 이 경로는 E2E로 따로 실행하지 않았다). README 한계에 이미 적혀 있다.
- **판단:** 사칭 방지와 맞바꾼 동작이라 버그로 보지 않는다. 사용자에게 보이는 안내 문구(`NAME_TAKEN`)가 "곧 자리가 비워진다"는 설명은 하지 않는다.

## 테스트 코드 자체의 오류 (제품 결함 아님, 정정 이력)

첫 실행에서 실패한 항목 중 제품 결함이 아닌 것들이다. 원본 로그는 `logs/e2e-*-first-run-with-test-bugs.log`에 그대로 있다.

| 첫 실행 실패 | 원인 | 정정 |
|---|---|---|
| 솔로 60판 전부 실패(`scene:0`), 건당 30초 | 현장 이미지를 **결과 화면으로 이동한 뒤** 측정했고, 없는 요소를 기본 30초 대기 | 이동 전에 측정, 타임아웃 5초 |
| 목록 화면 | 시즌 탭 텍스트를 `SEASON 1 (7)`로 가정, 실제 DOM은 공백 없이 이어짐 | 정규식 `SEASON 1 ?\(7\)` |
| 프로필 XSS | payload가 33자인데 프로필 이름 상한이 20자라 잘림 → 문자 그대로 표시될 수 없음 | 20자 이내 payload(`<svg onload=__x=1>`) |
| 팀 8인 8명 전부 실패 | 전적 `total`을 인원수(8)로 단언했으나 실제 값은 **문항 수(3)** | 단언을 `total === 3`으로, 항목별 진단 출력 추가 |
| 팀 XSS | 같은 20자 한도(팀 이름은 방장이 20자로 자름) + 로비 텍스트를 인원 동기화(2/8) 전에 읽음 | 20자 이내 payload, 2/8 대기 후 읽기 |
| 팀 로비 | 같은 이름 새 탭 재참가가 곧바로 성공할 것으로 가정 — 실제는 F3 | 유예 중 거부를 기대값으로, 22초 후 재참가 성공 확인 |
| 노트 새로고침 | 입력 후 600ms 대기 없이 새로고침 → F1에 걸림 | 600ms 대기 + F1을 별도 관찰 시나리오로 분리 |

변이 테스트 첫 시도도 같은 맥락이다. 신규 테스트가 18종 중 14종만 잡아, 놓친 4종(이름 중복 허용·답안 길이 제한·공개 중복 방지·포인터 좌표 보정)을 잡도록 퍼저의 정상 형식 비중을 높이고 경계 테스트(T3-F)를 추가했다.

## 미재현 일시 실패 (원인 미확정)

- **현상:** 개발 서버 전체 실행(`logs/e2e-dev-full.log`)에서 `solo s1e04 패턴=first` 1건 실패(332ms, 세부 항목은 그 시점엔 진단 출력이 없어 알 수 없음). 서브경로 빌드 전체 실행(89/89)과 직전 솔로 60/60 실행에서는 통과했다.
- **재현 시도:** 진단 항목(`failedChecks`)을 넣은 뒤 같은 시나리오 단독 30회 + 솔로 60판 전체 3회(180판) = **210판 연속 0건 실패.**
- **결론:** 일시적 현상으로 보이나 **원인은 모른다.** 실패 시점의 세부 항목이 남아 있지 않아 제품 결함인지 테스트 타이밍(예: 노트 입력 직후 제출)인지 가릴 수 없다. 같은 증상이 다시 나오면 `failedChecks`가 어떤 항목이 틀렸는지 알려준다.

## 2026-11-22 정정 (이 문서 작성 후 뒤집힌 내용)

- **"모바일 320/390/768에서 가로 스크롤 0" → 틀렸다.** 320폭 **목록 화면**은 331px로 넘친다(시즌 탭, 3엔진 재현, F4). 당시 E2E가 `isMobile` 에뮬레이션에서 넘침과 함께 커지는 `innerWidth`와 `scrollWidth`를 비교해 못 잡았고, 선언 뷰포트 너비로 비교하도록 고쳤다. 상세: [2026-11-22](../2026-11-22-cross-browser-and-hijack/README.md).
- **"미재현 일시 실패 `s1e04`"의 원인 추정:** 이후 WebKit에서 `sp02`가 같은 증상(전적은 정상, 결과 텍스트 검사 전부 false)으로 한 번 실패했다. 결과 화면 렌더 전에 텍스트를 읽은 테스트 경쟁 조건일 가능성이 높아 렌더 대기를 넣었다. **증명한 것은 아니며**, 수정 뒤 3엔진 × 솔로 60판 실행에서 솔로 실패는 0건이다.
